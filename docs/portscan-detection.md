# Port Scan Detection and Automated Response

## Overview

This project implements a lightweight network reconnaissance detection and response mechanism directly on the OPNsense firewall.

The mechanism uses the underlying PF firewall state tracking capabilities to identify a source generating an excessive number of new TCP connections within a short period of time.

When the configured threshold is exceeded, the source address is added to a PF overload table named:

```text
PortScan
```

A separate floating firewall rule then blocks traffic from addresses contained in this table.

The resulting workflow is:

```text
TCP Connection Burst
        |
        v
PF State Tracking
        |
        v
Connection Threshold
        |
        v
PortScan PF Table
        |
        v
Floating Block Rule
        |
        v
filterlog
        |
        v
Wazuh
```

This provides a basic automated detection-and-response capability without requiring an external IDS to perform the initial blocking.

---

# Security Objective

The purpose of this mechanism is to detect connection behavior that may indicate:

* Port scanning.
* Network reconnaissance.
* Automated probing.
* Excessive connection attempts.
* Potentially malicious network automation.

The mechanism is intentionally focused on **connection behavior**, rather than attempting to identify every possible type of network scan.

It should therefore be considered one layer of a broader security architecture.

---

# Why Detect Port Scanning?

Port scanning is commonly used during the reconnaissance phase of an attack.

An attacker may first attempt to identify:

* Which hosts are reachable.
* Which TCP ports are open.
* Which services are exposed.
* Which systems may be vulnerable.

A simplified attack lifecycle can therefore look like:

```text
Reconnaissance
      |
      v
Port Scanning
      |
      v
Service Enumeration
      |
      v
Exploitation
      |
      v
Lateral Movement
```

Detecting and blocking suspicious scanning behavior early can reduce unnecessary exposure and provide useful security telemetry.

---

# PF State Tracking

OPNsense uses PF as its packet-filtering engine.

PF maintains state information for network connections.

This means the firewall can track information associated with connections rather than treating every packet as an independent event.

The PortScan mechanism uses this capability to enforce connection limits.

The important distinction is:

```text
Packet filtering
       +
State tracking
       +
Connection limits
       =
Behavior-based enforcement
```

This makes the mechanism more useful than a simple static IP blocklist.

---

# Connection Threshold

The detection rule limits the number of new connections generated by a source within a configured time period.

During laboratory validation, the thresholds were deliberately made very aggressive:

```text
Max New Connections (c): 2
Max New Connections (s): 2
Time window: 5 seconds
```

These values were selected to make the behavior easy to reproduce in a controlled environment.

They are **not production recommendations**.

A normal browser can easily create several simultaneous connections, so these values would generate excessive false positives in a real network.

---

# Overload Table

The detection rule uses an overload table:

```text
PortScan
```

The overload table acts as a dynamic list of source addresses that have exceeded the configured connection threshold.

The current contents can be inspected from the OPNsense shell:

```bash
pfctl -t PortScan -T show
```

Example:

```text
192.168.10.2
```

indicates that the corresponding source address has been added to the table.

---

# Detection Process

The complete process can be represented as:

```text
                 New TCP Connections
                         |
                         v
                +------------------+
                | PF State Tracking|
                +--------+---------+
                         |
                         v
              Threshold exceeded?
                    /        \
                  NO          YES
                  |            |
                  v            v
             Normal flow   Add source
                              |
                              v
                       PortScan table
```

The firewall therefore does not need to identify the application generating the traffic.

It can react to the observed connection behavior.

---

# Blocking Process

A separate floating rule uses the `PortScan` table as its source.

Conceptually:

```text
IF source ∈ PortScan
THEN
    BLOCK
    LOG
```

The traffic flow becomes:

```text
Source IP
    |
    v
Is IP in PortScan?
    |
    +---- YES ----> BLOCK
    |
    +---- NO -----> Normal firewall evaluation
```

This separation between detection and enforcement makes the configuration easier to understand and maintain.

---

# Floating Rule Design

The PortScan blocking rule is implemented as a floating rule.

The important characteristics include:

* Floating rule.
* Quick processing.
* Block action.
* Logging enabled.
* Source based on the `PortScan` alias/table.

The detection rule is responsible for populating the table.

The blocking rule is responsible for enforcing the resulting decision.

This produces a two-stage architecture:

```text
Detection
   |
   v
PortScan
   |
   v
Enforcement
```

---

# Why `Quick` Matters

The blocking rule uses the `Quick` option.

This is important because a packet may potentially match multiple firewall rules.

The intended behavior is:

```text
Packet
  |
  v
Source in PortScan?
  |
 YES
  |
  v
QUICK
  |
  v
BLOCK
```

The packet is therefore not allowed to continue through later rules that might otherwise permit the traffic.

This is particularly important when broad pass rules exist elsewhere in the configuration.

1. The firewall observed the connection behavior.
2. The threshold was exceeded.

4. The blocking rule prevented further traffic.

# Automatic Response

Once an address is inserted into the `PortScan` table, blocking occurs automatically.

No administrator intervention is required for the initial response.

This can be represented as:

```text
Suspicious behavior
        |
        v
Detection
        |
        v
Dynamic blocklist
        |
        v
Firewall enforcement
```

This is a basic example of automated security response.

---

# Firewall Logging

The blocking rule has logging enabled.

When traffic from a blocked source is processed, OPNsense can generate a `filterlog` event containing information about the traffic.

The event can include:

* Interface.
* Direction.
* Action.
* Protocol.
* Source address.
* Source port.
* Destination address.
* Destination port.

This provides the telemetry required for centralized monitoring.

---

# Wazuh Integration

The `filterlog` event is forwarded to the Wazuh Manager through Syslog.

```text
OPNsense
192.168.20.1
      |
      | UDP 5514
      v
Wazuh Manager
192.168.20.2
```

The Wazuh Manager receives the event through `rsyslog` and monitors the resulting log file.

The event is then processed by Wazuh's analysis engine.

---

# Custom Detection Rule

A custom Wazuh rule was created for the project.

The rule ID is:

```text
100100
```

The rule is stored in:

```text
configs/wazuh/local_rules.xml
```

Its purpose is to identify the relevant OPNsense firewall event and generate a higher-level Wazuh security alert.

This creates an additional monitoring layer above the firewall's immediate enforcement.

# False Positives

Connection-rate detection has an important limitation: legitimate applications can generate large numbers of connections.

Examples include:

* Web browsers.
* Software updates.
* Package managers.
* Cloud applications.
* API clients.
* Parallel downloads.

Therefore, an extremely low threshold such as:

```text
2 connections / 5 seconds
```

is only appropriate for controlled testing.

Production deployments require tuning based on observed baseline traffic.

---

# Management Lockout Risk

A particularly important operational consideration is the possibility of blocking the administrator's own IP address.

During testing, the Management workstation was successfully added to the `PortScan` table.

This demonstrated that the mechanism was functioning correctly, but also highlighted a real operational risk.

An overly aggressive detection policy can lock out administrators.

Possible mitigations include:

* Excluding trusted administrative sources.
* Using higher thresholds.
* Creating administrative exceptions.
* Maintaining console access to the firewall.
* Having a documented procedure to clear the PF table.

For laboratory testing, the table can be cleared with:

```bash
pfctl -t PortScan -T flush
```

This should be treated as an administrative recovery mechanism rather than a normal operational procedure.

---

# Limitations

This mechanism is not intended to replace a dedicated IDS/IPS.

It primarily detects excessive connection creation.

It may not reliably detect:

* Very slow scans.
* Distributed scans.
* Scans using multiple source addresses.
* UDP reconnaissance.
* Application-layer reconnaissance.
* Highly stealthy techniques.

For this reason, the project treats the mechanism as one component of a layered security architecture.

# Security Engineering Considerations

The implementation demonstrates an important security-engineering trade-off:

```text
Detection Sensitivity
        |
        v
    False Positives
        |
        v
Operational Impact
```

Increasing detection sensitivity generally increases the probability of detecting suspicious activity, but it can also increase false positives.

The laboratory therefore uses aggressive values for demonstration while documenting the need for production tuning.

This distinction between **demonstrating a control** and **deploying the control safely** is an important part of the project.

---

# Summary

The PortScan mechanism demonstrates a complete network-level detection and automated response workflow.

The firewall:

1. Tracks connection state.
2. Detects excessive new connections.
3. Adds the source to the `PortScan` PF table.
4. Blocks subsequent traffic.
5. Logs the event.
6. Forwards the event to Wazuh.
7. Allows Wazuh to generate a security alert.

The result is a practical example of:

**Detection → Enforcement → Logging → SIEM Monitoring**

implemented entirely within the laboratory environment.
